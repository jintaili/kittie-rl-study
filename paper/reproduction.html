Delay input and control loop

timing.py expresses the single-request scheduling rules. Measured mode applies a response when ready. Floor mode waits until both the supplied target frame and the actual response-ready frame have been reached. The next observation follows action application by the configured number of frames. Terminal responses are loggable but cannot be applied. Tests cover early and late replies, request overlap, terminal replies, one-frame intervals and exhaustion of the supplied schedule.

Timing input contains the existing per-scenario delay schedules. It is a supplied input object. The package does not need code that reconstructs an empirical delay distribution. This scheduling reference still needs a native-emulator integration; it is not presented as a tested replacement for the study's retained control loop.

Shortest path through the study

  1. Start from the pinned pretrained Qwen model with a fresh LoRA adapter. Train five Courtyard BC epochs, then four multi-level BC epochs using the successful JEV trajectory splits. Start a fresh optimizer at the multi-level stage to obtain BC04. Alternatively, use the supplied Courtyard adapter to skip the first stage while preserving the actual initialization.
  2. Initialize the PPO value head from the supplied warmup input, then run 16 sequential Head Goon PPO iterations with continuous actor, critic, optimizer and RNG state. Retain iteration checkpoints, including PPO15 and the secondary PPO10 checkpoint.
  3. Evaluate BC04 and PPO15 greedily under the original six-frame protocol. PPO10 is an optional secondary checkpoint analysis.
  4. Evaluate the same frozen policies on the 50 supplied randomized scenarios. Use the same saved native entries and schedules, with current information observable and future draws hidden.
  5. Evaluate JEV on the original encounter and the same randomized scenarios. Compute the main paper tables using the exported per-game schema. The separate delay and one-frame interventions are supplementary analyses; their reproduction is optional for the main comparison. Supply the delay-floor schedule directly when reproducing that intervention.

study.json identifies the model, prerequisite assets and checkpoint hashes. scenarios.json contains the 50 existing scenarios. Evaluation-only reproduction can start from the frozen BC04/PPO15 checkpoints and omit training. A fresh training run should not be expected to produce identical weights or real-time trajectories. Omitting historical monitoring can also change RNG consumption; the minimal path targets the stated training method, not bitwise regeneration of the historical checkpoints.

Still required before release

The next implementation step is to consolidate the successful BC and PPO stages into minimal training entry points and package the native evaluation dependencies, pinned environment and model assets. That work must preserve the initialization, critic warmup and sequential training state that produced the reported checkpoints. The reported checkpoint was chosen using the subsequent 50-game evaluations. Historical training also included sampled monitoring games; those games did not supply training targets or determine which training state continued. They remain documented in the original run records and are not a required selection step in the minimal reproduction path. Failed launches, unrelated training branches, historical monitoring code and repeated exploratory evaluations do not belong in the reader's execution path.

The BC04 randomized evaluation is complete and audited. Its 50 games and matched PPO15 comparison are included in the exported data and analysis. The offline package reproduces the +18 percentage-point difference, paired interval of 0 to 36 points and exact McNemar p = 0.0784. Training and evaluation packaging remains incomplete as described above.
